# Java 后端开发工程师 知识库

## 核心技术栈
Java 后端岗位要求掌握：Java 语法与集合框架、JVM 内存管理与调优、并发编程（线程、锁、JUC）、Spring/Spring Boot 生态、MySQL 数据库与 SQL 优化、Redis 缓存、消息队列（RabbitMQ/Kafka）、分布式系统基础（CAP、分布式锁、幂等）。加分项：Docker/K8s、微服务（Spring Cloud）、网络编程（Netty）。

## 考点：HashMap 底层原理
HashMap 底层是数组+链表+红黑树。put 时对 key 的 hashCode 做扰动运算（高16位异或低16位）减少碰撞，再与 (n-1) 按位与定位桶下标。碰撞时以链表存储；JDK 8 引入优化：链表长度超过 8 且数组长度达到 64 时转化为红黑树，查询从 O(n) 优化为 O(logn)；节点数降到 6 时退化回链表。负载因子默认 0.75，元素数超过 容量×0.75 触发扩容为 2 倍并重新散列。JDK 8 将头插法改为尾插法，修复了并发扩容时链表成环导致的死循环（但 HashMap 仍然线程不安全，并发场景应使用 ConcurrentHashMap）。

## 考点：Java 内存模型（JMM）与 volatile
JMM 定义了主内存与线程工作内存的抽象，规范了多线程读写共享变量的可见性、有序性与原子性。volatile 两个语义：1）可见性——写 volatile 变量立即刷回主内存并使其他线程的缓存行失效；2）有序性——通过内存屏障禁止指令重排，遵循 happens-before 原则。volatile 不保证原子性：i++ 是"读-改-写"三步操作，并发下仍会丢失更新，需用 AtomicInteger 或锁。典型应用：双重检查锁单例中防止指令重排（new 对象的 分配内存→初始化→赋值引用 可能重排）。

## 考点：线程池
ThreadPoolExecutor 七大参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（空闲存活时间）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）、unit。执行顺序：核心线程 → 队列 → 非核心线程 → 拒绝策略。四种拒绝策略：AbortPolicy（抛异常，默认）、CallerRunsPolicy（调用者执行，起到限流作用）、DiscardPolicy、DiscardOldestPolicy。配置经验：CPU 密集型设 N+1（N=核数），IO 密集型可设 2N 左右或按 N×(1+等待时间/计算时间) 估算；生产环境务必使用有界队列防止 OOM，并自定义拒绝策略记录日志告警。推荐用 ThreadPoolExecutor 手动创建而非 Executors 静态方法（FixedThreadPool 无界队列、CachedThreadPool 可能无限创建线程）。

## 考点：Spring Bean 生命周期
流程：1）实例化（构造器/工厂方法）；2）属性注入（依赖注入）；3）Aware 回调（BeanNameAware、ApplicationContextAware 等）；4）BeanPostProcessor 前置处理；5）初始化（@PostConstruct → InitializingBean.afterPropertiesSet → init-method）；6）BeanPostProcessor 后置处理（AOP 代理通常在此生成）；7）使用；8）销毁（@PreDestroy → DisposableBean.destroy → destroy-method）。@Autowired 是 Spring 提供的，按类型注入（byType），配合 @Qualifier 指定名称；@Resource 是 JSR-250 标准，默认按名称（byName）注入，找不到再按类型。Spring 通过三级缓存解决单例 Bean 的 setter 循环依赖，但构造器循环依赖无法解决。

## 考点：MySQL 索引失效与慢 SQL 排查
常见索引失效场景：1）违反最左前缀原则（联合索引 a,b,c 跳过 a 直接查 b）；2）对索引列使用函数或运算（WHERE YEAR(create_time)=2024）；3）隐式类型转换（字符串列用数字比较）；4）LIKE 以 % 开头；5）OR 连接非索引列；6）优化器判断全表扫描更快（回表代价高）。慢 SQL 排查步骤：1）开启慢查询日志（long_query_time）定位 SQL；2）EXPLAIN 分析执行计划，重点关注 type（至少 range，最好 ref/const）、key（实际用到的索引）、rows（扫描行数）、Extra（Using filesort/temporary 需警惕）；3）优化手段：建合适索引、覆盖索引避免回表、改写 SQL、分页深度优化（延迟关联）、必要时分库分表。

## 考点：缓存一致性
Cache Aside 模式：读——先读缓存，未命中读库并回填；写——先更新数据库，再删除缓存（不是更新缓存，避免并发写导致脏数据及冷数据浪费）。为什么先更新库再删缓存：反过来在删缓存后、更新库前的窗口期，读请求会把旧值回填。残留问题及对策：1）更新库成功但删缓存失败——设置缓存过期时间兜底 + 消息队列重试删除；2）读写并发下的短暂不一致——延迟双删（写后延迟几百毫秒再删一次）；3）更彻底的方案——基于 binlog 订阅（Canal）异步删除，保证最终一致。

## 考点：短链接系统设计
核心是短码生成与跳转。方案一：发号器——自增 ID 经 62 进制编码生成短码，简单、无冲突，可预生成号段提升性能；方案二：哈希——对长 URL 做 MurmurHash 后截取，冲突时探测或加盐重试，需要查库判重。存储：MySQL 存长短映射（短码唯一索引），热点数据 Redis 缓存，读写比通常 100:1 以上，缓存命中率是关键；可加布隆过滤器拦截不存在的短码防穿透。跳转用 302（临时重定向）而非 301，因为 301 会被浏览器缓存，无法统计点击、也无法改指向。容量估算：日访问百万级，QPS 峰值按日流量/86400×3~5 倍估算，单机 Redis 足以支撑，重点做好缓存与水平扩展。

## 考点：线上接口突变的处理思路
原则：先止血、再定位、后复盘。1）止损：限流降级、回滚最近发布、扩容，优先恢复服务；2）定位：看监控大盘确定故障层（网关→应用→DB→下游依赖）；应用层看 GC 日志（Full GC 频繁？）、线程池（打满？慢查询）、CPU/内存；DB 层看慢 SQL、锁等待；3）常见原因：慢 SQL、缓存失效打爆 DB（缓存雪崩）、发布引入 bug、流量突增、下游超时连锁；4）复盘：补监控告警、压测预案、代码 review。

## 行为面试要点（后端）
自我介绍结构：基本信息（10秒）→ 技能栈与匹配点（30秒）→ 最有代表性的项目与量化成果（40秒）→ 求职意向（10秒），总时长控制在 1.5~2 分钟，不背简历全文。技术分歧的处理范式：先完整倾听对方方案及理由 → 陈述自己的方案与依据 → 用数据/基准测试/小流量验证代替口头争论 → 以共同目标（稳定性、性能、交付时间）做决策 → 结论无论采纳谁，都对事不对人。回答用 STAR 结构（情境-任务-行动-结果），结果要有数字。

## 优秀回答范例
范例（线程池配置）：「我会先分析任务特征。假设是处理文件上传后的异步解析，属于 IO 密集型，单任务平均 200ms 计算 + 800ms 等待 IO。按 N×(1+W/C) 估算，4 核机器可以设 16 左右核心线程；队列用有界的 LinkedBlockingQueue，容量按可接受的最大积压设 1000，防止 OOM；拒绝策略我会自定义，先记录任务元信息并告警，再按业务决定丢弃或降级；线程名通过 threadFactory 显式命名，方便排查问题。上线后我会根据监控里队列积压和线程活跃度再调参。」——要点：有估算公式、有防御性设计、有上线后迭代意识。
